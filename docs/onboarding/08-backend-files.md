# 8. Every file under `backend/`

**How to read this chapter.** Files are grouped by folder. Each file is marked:

- **[P]** — product / hand-written. Your team owns and edits it.
- **[G]** — generated by `app_gen`. Do not hand-edit; change the model and
  regenerate (chapter 3.5).
- **[G-once]** — generated **once** as a stub, then hand-owned. `app_gen` will
  not overwrite it. This is where custom-method bodies live.

The four biggest generated files (`handlers/governance/mod.rs` 8,193 lines,
`operations/generated.rs` 6,951, `handlers/governance/generated.rs` 7,127,
`schemas/governance.rs` 5,783) are explained once as patterns — reading them
top to bottom is not useful; they are 24 near-identical repetitions.

## 8.1 `backend/Cargo.toml`, `backend/.env`, `backend/Dockerfile`

| File | | Notes |
|------|--|-------|
| `Cargo.toml` | [P] | Crate manifest. Features `http` + `provider-postgres` on by default; `mcp`/`kafka`/`sync` off. Framework crates as path deps to `../../app-framework/*`. The `[lints.rust] non_camel_case_types = "allow"` is there because the generator emits SCREAMING_SNAKE enum variants. |
| `.env` | [P] | Git-ignored local config. Non-secret runtime vars + **real** `GRAPH_*` / `OPENAI_*` secrets (see chapter 4.7). |
| `Dockerfile` | [P] | 3-stage build: (1) `node` builds the SPA to `product_dist/`, (2) `rust` builds `backend` release binary (needs the framework checkout in context), (3) `debian-slim` runtime image with the binary + `config/` + `product_dist/`. Build context is the **parent** dir. |
| `Dockerfile.dockerignore` | [P] | Excludes `target/`, `node_modules/`, `.env` from the image build context. |
| `README.md` | [P] | Layout + ownership table + run commands. |
| `product_dist/**` | [G] | The built SPA (from `npm run build`). Committed so the backend image has a UI without a Node build. `assets/` holds the hashed JS/CSS bundles. |

## 8.2 `backend/src/` top level

| File | | What it does |
|------|--|--------------|
| `main.rs` | [P] | Binary entry point. Builds the Tokio runtime **by hand** with a 128 MiB worker stack (avoids a deep-recursion stack overflow in the read path — see the doc comment). Loads `.env`, tracing, `SecurityConfig` (exits on unsafe config), `RuntimeMode`, `AppConfig`, `RuntimeAuthState`, then `routes::get_routes` and `serve_http_router`. This is *the* place product code can inject things `routes/mod.rs` (generated) can't own — e.g. the not-yet-built Graph webhook router (see `docs/architecture/meeting-graph-gaps.md`). |
| `lib.rs` | [P] | Three constants: `APP_NAME`, `PRODUCT_SCHEMA`, `BACKEND_PROVIDER` = `"governance"`, `"governance"`, `"PostgreSQL"`. The library crate exists only to expose these. |
| `product_api.rs` | [P] | The internal API surface handlers/services/operations import. Re-exports `UserAuth`, `PolicyAccess`, `DataAccess`, `AppError`, `EntityType`, `HandlerResult`, `JsonValue`, and the runtime model-metadata types under one path. Contains the `runtime_*_metadata` / `runtime_data_type` / `product_data_type` conversions between this crate's `schemas::system` types and the framework's `RuntimeModelMetadata` — this is the "translate our config shape into the framework's shape" layer. Also `user_from_context` / `data_access_from_context` (pull `UserAuth` / `DataAccess` off a GraphQL context). |
| `admin_ui.rs` | [P] | Implements the framework's `Admin*Provider` traits (model view, schema summary, policy explain, audit timeline, query diagnose) against this crate's `AppConfig` / `DataAccess`, and mounts `/admin/*`. `http`-feature only. The audit-timeline provider is what surfaces the hash-chained `<entity>_audit` history for one record. |

## 8.3 `backend/src/config/` — configuration loading [all P]

| File | | What it does |
|------|--|--------------|
| `mod.rs` | [P] | 7 lines — declares `loader` and `app_config`. |
| `loader.rs` | [P] (370 ln) | `read_config()` — reads `backend/config/generated/`: `data_sources.yaml`, and per Postgres-schema `schema.yaml` + `entity_types.yaml` + every `*.rego`. `add_secrets(data_source)` resolves DB credentials from env vars (`PG_SERVICE_ACCOUNT_NAME`/`_PASS`, keyed by provider type — MSSQL/Fabric are explicitly rejected: Postgres-only) and pins the single active environment (`ENV_NAME`). `validate_environment_security` checks TLS/security-profile via the framework's `connection_security`. `load_policy` compiles each `.rego` into a `regorus::Engine`. `apply_schema_data_source_override` lets `APP_<SCHEMA>_DATA_SOURCE_NAME` / `APP_DATA_SOURCE_NAME` env vars repoint a schema. |
| `app_config.rs` | [P] (460 ln) | The `AppConfig` struct: `sources`, `_schemas`, `types` (entity metadata by `schema.PascalName`), `access` (Rego engines by `schema.snake_name`), all behind `Arc<HashMap<...>>`. **`evaluate_user_access(entity, action, user)`** is the security heart: serialises the user, builds the Rego `input`, honours `bypass_policies_in_local` / `allow_missing_policies_in_local` (with warnings), runs `data.<schema>.<entity>.access`, parses the result into a `PolicyAccess { allow, filter }`, then calls `tenant_isolation::apply`. Also entity/property lookup helpers, primary-key resolution, the native `record_locator` synthetic property, nav-entity resolution. |

## 8.4 `backend/src/platform/` — thin wiring over the framework [all P]

| File | | What it does |
|------|--|--------------|
| `mod.rs` | [P] | Declares the submodules and provides **narrow re-export modules** so the rest of the crate has stable `crate::platform::*` paths to framework contracts: `identifier` (`appfw_runtime::identifier::*`), `policy` (`AccessAction`, `PolicyAccess`), `record_locator`, `user_auth` (`RuntimePrincipalType`, `UserAuth`). |
| `runtime.rs` | [P] | Two lines of real code: `pub use appfw_runtime::*;` — a glob re-export so `crate::platform::runtime` is an alias for the whole framework runtime crate. |
| `secrets.rs` | [P] | The `SecretProvider` trait (`get_secret` / `require_secret`) and `EnvSecretProvider` (reads env vars, treats empty as absent). The trait exists so a real secret manager can be swapped in later without touching callers. |
| `tenant_isolation.rs` | [P] | `is_tenant_scoped(entity)` — true iff the entity has a real (non-nav) `tenant_id` scalar. `apply(entity, user, access)` — for a tenant-scoped entity, `_and`-merges a `{tenant_id: {_eq: user.tenant_id}}` filter into the policy result (or denies if the user has no tenant). **No governance entity has `tenant_id`, so this is currently a no-op** — but it's the mechanism that would enforce isolation if one did. |

## 8.6 `backend/src/schemas/` — GraphQL DTOs

| File | | What it does |
|------|--|--------------|
| `mod.rs` | [G] | Declares `common`, `governance`, `system`. |
| `common.rs` | [P] | Shared generic types: `QueryResult<T>` and `AggregateResult` (the pagination-wrapper shapes), plus `Login` / `InputLogin` / `LoginResultProjection` / `Claims` — **auth DTOs that are declared but currently unused** (`#[allow(dead_code)]`) — the placeholder for a future real password-login mutation. |

## 8.7 `backend/src/handlers/` — GraphQL resolvers

### The shape

```
handlers/
├── mod.rs                       [G]  declares governance + system; pagination_args helper
├── selections.rs                [G]  parses the GraphQL selection set into the JSON the data layer wants
├── governance/
│   ├── mod.rs                   [G]  GovernanceQuery + GovernanceMutation objects (8,193 ln)
│   ├── generated.rs             [G]  the default CRUD _impl fns per entity (7,127 ln)
│   ├── <entity>.rs              [G-once] × 24  product override file
│   ├── <entity>_audit.rs        [G-once] × 21  product override file (audit companions)
└── system/
    ├── mod.rs                   [G]  SystemQuery + SystemMutation
    ├── generated.rs             [G]  default CRUD for system entities
    ├── schema.rs                [G-once]  product override
    └── entity_type.rs           [G-once]  product override
```

### `governance/mod.rs` [G] — the resolver objects

For **every** entity, `GovernanceQuery` gets `find_<entity>`,
`find_<entity>_by_locator`, `get_<entities>`, `query_<entities>`,
`aggregate_<entities>`; `GovernanceMutation` gets `create_<entity>`,
`update_<entity>`, `delete_<entity>`, plus one method per **custom method** in the
model. Each resolver is ~15 identical lines: `from_context(ctx, "governance",
"<Entity>")` → `into_handler_parts()` → call `<entity>::<op>_impl(...)` → map
`Ok`/`Err`. 8,193 lines = ~330 near-identical resolvers.

### `governance/generated.rs` [G] — the default implementations

Per entity, a module `<entity>` containing `find_impl`, `find_by_locator_impl`,
`get_impl`, `query_impl`, `create_impl`, `update_impl`, `delete_impl`. Each is a
thin call into `DataAccess` (`find_item` / `query_items` / `create_item` / …).
7,127 lines = 24 repetitions.

### `governance/<entity>.rs` [G-once] — the override files

Every entity has one. For an entity with **no custom logic** it is 8 lines:

```rust
//    Product-owned handler extension file. Generated once by app_gen, then preserved.
#[allow(unused_imports)]
pub(crate) use super::generated::comment::*;
```

i.e. "use all the generated defaults unchanged." This is true for:
`attachment`, `attachment_audit`, `audit_event`, `checklist_item(+_audit)`,
`comment(+_audit)`, `email_queue_item`, `gate_review_audit`,
`gate_submission_audit`, `graph_subscription`, `graph_write_attempt`,
`knowledge_chunk`, `knowledge_document`, `meeting_audit`, `notification`,
`project_approval_audit`, `project_audit`, `project_field(+_audit)`,
`project_stakeholder(+_audit)`, `risk_item(+_audit)`, `task_assignment(+_audit)`,
`user_audit`, and every `workflow_*(+_audit)`.

The ones with **real hand-written bodies** (each `pub use`s the generated
defaults for standard CRUD, then adds `<name>_impl` functions):

| File | Custom `_impl`s → service call |
|------|-------------------------------|
| `project.rs` | `submit_decision_impl`→`approval_state_machine::submit_decision`; `pending_approvals_impl`→`…::pending_approvals`; `fast_track_complete_impl`→`…::fast_track_complete`; `workspace_impl`→`workspace::assemble`; `eligible_gates_impl`→`gate_eligibility::compute`; `cancel_impl`→`…::cancel`; `extract_intake_impl`→`ai_extraction::extract_intake`; `extract_team_fields_impl`→`ai_extraction::extract_team_fields` |
| `gate_review.rs` | `decide_impl`→`gate_review::decide` |
| `gate_submission.rs` | `save_stage_impl`→`transition::save_stage` |
| `workflow_stage.rs` | `start_impl`/`submit_impl`/`skip_impl`→`transition::{start,submit,skip}` |
| `meeting.rs` | `schedule_via_graph_impl`→`meeting_scheduling::schedule_via_graph`; `cancel_via_graph_impl`→`meeting_scheduling::cancel_via_graph`; `process_transcript_impl`→`meeting_transcript::process_transcript` |
| `user.rs` | `search_directory_impl`→`directory::search_directory` |

Every `_impl` is 1–4 lines. **All logic is in `services/`.**

### `governance/generated.rs`, `mod.rs`, `selections.rs`, `system/*`

`selections.rs` [G] — `get_query_selections(ctx)` walks the async-graphql
selection AST and produces the `{name, selection_set:[...]}` JSON tree the data
layer consumes (the same shape services build by hand with `field()`/`selection()`).
`system/schema.rs` and `system/entity_type.rs` [G-once] are 6-line "use the
generated defaults" files.

## 8.9 `backend/src/data/` — the data-access layer [all P, but mostly mechanical]

This folder is product-owned but is a thin, mostly-mechanical wrapper over
framework contracts — it exists so the product can (a) name framework things via
its own module paths, (b) add a hook or two, (c) keep the audit-hash-chain types
local. Real custom logic here is minimal.

| File | | What it does |
|------|--|--------------|
| `mod.rs` | [P] | Folder overview; declares submodules. |
| `data_access.rs` | [P] | The `DataAccess` struct (`app_config` + `DatabaseClientBox` + `MetricsRegistry`) and its public API: `find_item`, `get_items`, `query_items`, `batch`, `aggregate_items`, `create_item`, `update_item`, `delete_item`, custom-method dispatch, `query_audit_events`, `diagnose_query`, `health_check`, `pool_stats`, `provider_descriptor`. Delegates to `read_orchestration` / `mutation_orchestration`. `ensure_provider_operation` — fail closed if the provider doesn't declare an operation. |
| `read_orchestration.rs` | [P] | The read pipeline: **validate → authorize (`evaluate_user_access`) → fetch → evaluate (projections/computed) → trace**. `QueryPlanDiagnostic` — the redaction-safe "how would this query run" explainer used by the admin UI. |
| `mutation_orchestration.rs` | [P] | The create/update/delete pipeline: pre-mutation validation (PK availability, FK existence, uniqueness — the FK/uniqueness checks reuse the read wrappers), execution, and the audit-attempt/audit-mutation append helpers built on `data::audit_event::AuditEvent`. |
| `query_ir.rs` | [P] | The provider-agnostic query **intermediate representation**: filter AST, sort spec, selection tree, cost inputs. `cost_for_query`, `QueryPlan`, `AggregatePlan`, `MutationPlan`, `PaginationPolicy`. |
| `query_ir_validation.rs` | [P] | Pure leaf validators/parsers for aggregate functions + sort directions, and `From` conversions to `appfw_runtime::query_ir`. Pagination + the signed keyset cursor are framework-owned, not here. |
| `provider_plan.rs` | [P] | Resolved/validated plan value types shared between the IR and the client: the pagination window + strategy (with env-driven bounds), and `ProviderMutationPlan` / `MutationKind`. |
| `provider_identity.rs` | [P] | `ProviderDescriptor`, the operation-contract types (`Required` / `Optional` / `LegacyCompatibility` support levels), pool-stats shape — the slice of provider identity `DataAccess` needs without pulling in framework internals. |
| `data_access.rs` … `audit_event.rs` | [P] | `AuditEvent` — the 21-field, SHA-256 hash-chained audit record: construction, redaction, diffing, `event_hash` finalisation chained via `prev_hash`. Converts to/from `appfw_runtime::RuntimeAuditEvent`. The serialization shape + hash are a **compatibility contract** with already-persisted history — don't change them casually. |
| `rules/mod.rs` | [P] | Per-record create/update rules: evaluate `computed` properties, stamp the `version` (optimistic concurrency) field, timezone-normalise, run field validation. `evaluate` is the single entry point from the mutation path. |
| `clients/mod.rs` | [P] | Declares `database_client` + `postgres`. |
| `clients/database_client.rs` | [P] | The `DatabaseClient` **trait** (provider-agnostic: find/query/aggregate/mutate/explain, audit append/read, custom-method exec) + `DatabaseClientRuntimeAdapter` (wraps a `DatabaseClient` to implement the framework's `RuntimeProviderIdentity` / `RuntimeProviderDataClient`). `DatabaseClientBox` = `Box<dyn DatabaseClient>`. |
| `clients/postgres/mod.rs` | [P] | Declares `postgres_client` + `cte` + `filter`. |
| `clients/postgres/postgres_client.rs` | [P] | `PostgresClient` — the `DatabaseClient` impl over a `deadpool_postgres` pool. `init(app_config, data_source_name)` opens the pool. Translates resolved plans into SQL via `cte` + `filter` + `appfw_provider_postgres`, executes, maps driver errors to `AppError`. |
| `clients/postgres/cte.rs` | [P] | Builds the common-table-expression SQL that assembles nested selections — navigation joins, many-to-many junctions, `json_agg` projection — wrapping `appfw_provider_postgres` primitives. |
| `clients/postgres/filter.rs` | [P] | Lowers the query-IR filter AST into parameterised Postgres predicates, including `EXISTS (...)` subqueries for filtering on nav/FK relationships. This is where a Rego `{"manager_id": {"_eq": ...}}` filter becomes `AND manager_id = $n`. |
| `clients/postgres/README.md` | [P] | Notes on the Postgres client internals. |
