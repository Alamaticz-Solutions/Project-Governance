## 2.1 The two repositories

```
C:\Users\ManojRajakumar\Governance-Restructure\
├── app-framework\        ← the PDS App Framework (a separate product)
└── project-governance\   ← THIS repo: the governance application
```

They are **siblings** — two folders next to each other. `project-governance`
does not contain a copy of the framework; it refers to it by relative path
(`../app-framework/...`). Both are Git repos with their own history.

- **`app-framework`** is a general-purpose engine for building schema-driven
  Rust apps. It is not specific to governance. It contains the runtime library
  (`appfw_runtime`), the database providers (`appfw_provider_postgres` and a
  dozen others for Salesforce, Workday, Snowflake, ...), the code generator
  (`app_gen`), and the CLI (`appfw_cli`). Your team treats it as a black box that
  occasionally needs a patch (see `app-framework/PATCHES.md`).
- **`project-governance`** is the application: the model, the hand-written
  business logic, the frontend, the generated output, and the configuration.

Chapter 3 is entirely about this relationship. For now, just know the framework
lives next door and is pinned to an exact commit.

## 2.2 The layer cake (a request from top to bottom)

When the browser asks for data, the request passes through these layers. Every
layer is labelled with where its code lives.

```
┌─────────────────────────────────────────────────────────────────┐
│ BROWSER — React SPA                                              │
│ frontend/src/**   screens, routing, the GraphQL client          │
└───────────────┬─────────────────────────────────────────────────┘
                │  HTTP + JWT bearer token
                │  POST /governance   { GraphQL query }
                ▼
┌─────────────────────────────────────────────────────────────────┐
│ HTTP + GraphQL server  (framework: appfw_runtime; wiring:        │
│ backend/src/main.rs, backend/src/routes/**)                      │
│  • CORS, auth extraction (JWT → UserAuth), depth/complexity caps │
└───────────────┬─────────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────────┐
│ GraphQL handlers  (backend/src/handlers/**)                      │
│  • generated.rs — standard CRUD + query + aggregate per entity   │
│  • <entity>.rs   — hand-written custom-method _impl bodies       │
└───────────────┬─────────────────────────────────────────────────┘
                ├───────────────► SERVICE LAYER (hand-written)
                │                 backend/src/services/**
                │                 workflow engine, MS Graph, AI extraction
                ▼
┌─────────────────────────────────────────────────────────────────┐
│ DataAccess  (backend/src/data/**)                                │
│  • builds an internal query plan (query_ir)                      │
│  • RBAC: runs the Rego policy for (user, action, entity)         │
│  • tenant isolation filter (no-op here — single tenant)          │
│  • validation, mutation orchestration, audit hash-chaining       │
└───────────────┬─────────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────────┐
│ Database provider  (framework: appfw_provider_postgres)          │
│  backend/src/data/clients/postgres/** is a thin product wrapper  │
│  • turns the query plan into SQL, runs it on the connection pool │
└───────────────┬─────────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────────┐
│ PostgreSQL — database `governance`                               │
│  Postgres schema `governance` (24 business tables + *_audit)     │
│  Postgres schema `system` (framework metadata)                   │
└─────────────────────────────────────────────────────────────────┘
```

Key point: **the policy check happens inside `DataAccess`, before any SQL runs.**
A handler cannot "forget" to check permissions — the only path to the database is
through `DataAccess`, and `DataAccess` always evaluates the Rego policy first.

## 2.3 What is generated vs. hand-written

| Layer | Generated by `app_gen` | Hand-written (your team owns) |
|-------|------------------------|------------------------------|
| Model | — | **`.appfw/model/**`** (the source of truth) |
| DB DDL / seed SQL | `database/_pkg/**`, `backend/config/generated/**` | — |
| GraphQL schema types | `backend/src/schemas/governance.rs`, `system.rs` | `backend/src/schemas/common.rs` (small shared bits) |
| Route wiring | `backend/src/routes/mod.rs`, `governance.rs`, `system.rs`, `operations/generated.rs` | `backend/src/routes/info.rs`, `app_error.rs` |
| CRUD handlers | `backend/src/handlers/**/generated.rs`, `handlers/**/mod.rs`, `handlers/selections.rs` | — |
| Custom-method stubs | the empty `<name>_impl` fn, once | **the body of every `_impl`**, in `handlers/governance/<entity>.rs` |
| Business logic | — | **`backend/src/services/**`** |
| Platform wiring | — | **`backend/src/platform/**`**, `backend/src/config/**`, `backend/src/data/**`, `backend/src/main.rs`, `backend/src/admin_ui.rs`, `backend/src/product_api.rs` |
| Access policies | boilerplate wrapper + copy to `backend/config/generated/**` | **`.appfw/model/schemas/governance/rbac/*.rego`** (bodies) |
| Frontend contract | `frontend/src/generated/**` | everything else under `frontend/src/**` |

`backend/src/data/**` is interesting: it is product code, but it is a thin,
mostly-mechanical wrapper over framework types (it exists so the product can name
framework things through its own module paths and add a hook or two). Treat it as
"product-owned, but don't expect much custom logic there."

## 2.4 The code-generation pipeline

```
   .appfw/model/**  (YAML: entities, enums, relationships, rbac, seeds, manifest)
        │
        │   scripts/appfw product generate
        │   (runs app_gen from ../app-framework, on Windows inside a Linux container)
        ▼
   ┌──────────────────────────────────────────────────────────────┐
   │ generated outputs, written back into THIS repo:              │
   │  • backend/src/routes/{mod,governance,system}.rs            │
   │  • backend/src/schemas/{governance,system}.rs               │
   │  • backend/src/handlers/**/generated.rs, mod.rs, selections │
   │  • backend/src/operations/generated.rs                      │
   │  • backend/config/generated/**  (schema JSON/YAML + rego)   │
   │  • database/_pkg/**  (DDL + seed SQL, all dialects)         │
   │  • frontend/src/generated/**  (UI contract)                 │
   │  • podman-compose.yml                                        │
   │  • appfw.lock  (provenance hashes, see chapter 3)           │
   └──────────────────────────────────────────────────────────────┘
        │
        │   cargo build   (backend compiles model-derived code + your services)
        │   npm run build (frontend compiles, emits to backend/product_dist/)
        ▼
   runnable backend binary + static SPA bundle
```

You do **not** run the generator during normal development unless you change the
model. The generated files are committed, so a fresh clone builds without the
generator. You run it when:

- you edit anything under `.appfw/model/`, or
- you bump the framework version (chapter 3), or
- CI checks drift: `scripts/appfw product generate --check` re-runs the
  generator and fails if the committed output no longer matches.

## 2.5 Runtime topology (what actually runs)

From [`.appfw/manifest.yaml`](../../.appfw/manifest.yaml):

- **One process**: the `backend` binary. No workers, no queue consumers.
- **One database**: PostgreSQL, data source name `pg_primary`, hosting both the
  `governance` and `system` Postgres schemas.
- **One HTTP ingress**: `governance-http`, path `/governance`, consumed by the
  browser and by service-to-service API callers.
- **MCP ingress**: defined but **disabled**.
- **Kafka ingress** (`governance.events`): defined but **disabled**.
- **Product SPA**: built into the backend image, served at `/` when
  `APP_PRODUCT_UI_ENABLED=true`. Single-image deployment.
- **Admin UI**: the framework ships an admin UI (`backend/src/admin_ui.rs` wires
  it) — available for local/framework operations, **not** embedded in the
  product image.
- **Single-tenant.**

### Ports (local development)

| Port | Who | Notes |
|------|-----|-------|
| 8080 | backend HTTP | `API_PORT` in `backend/.env`; GraphQL at `/governance` and `/system`, admin at `/admin`, health at `/health/*`, metrics at `/metrics` |
| 5173 | Vite dev server | `frontend/vite.config.ts`; proxies `/governance`, `/system`, `/admin` to 8080 |
| 5432 | PostgreSQL | `podman-compose.yml` `postgres` service |
| 3001 | Grafana | only with the `observability` compose profile |
| 9093 | Alertmanager | only with the `observability` compose profile |

(The `podman-compose.yml` `backend` service defaults to port 3000, but the
hand-run local backend and the Vite proxy both use 8080 — the compose `backend`
service is not the normal local dev path; running `cargo run -p backend` directly
is.)

## 2.6 Endpoint map

| Path | Method(s) | What | Auth |
|------|-----------|------|------|
| `/governance` | POST | GraphQL for the 24 business entities + custom methods | JWT; every op runs a Rego policy |
| `/governance` | GET | GraphiQL explorer (introspection) | restricted by role in prod |
| `/system` | POST/GET | GraphQL for framework metadata entities | JWT |
| `/admin/*` | GET/POST | Framework admin runtime (model view, policy explain, audit timeline, query diagnose) | JWT + admin |
| `/health/live`, `/health/ready` | GET | Liveness / readiness (readiness pings the DB) | open |
| `/metrics` | GET | Prometheus metrics | open |
| `/` and SPA assets | GET | The React app | open (the app itself requires login) |
| `/internal/graph/notifications` | POST | *Planned*, not built — Microsoft Graph webhook for transcript auto-processing (see [`docs/architecture/meeting-graph-gaps.md`](../architecture/meeting-graph-gaps.md)) | client-state verified |

## 2.7 External systems the backend talks to

| System | Why | Where | Status |
|--------|-----|-------|--------|
| PostgreSQL | all persistent data | `appfw_provider_postgres` + `backend/src/data/clients/postgres/**` | required, always on |
| Microsoft Graph | schedule/cancel Teams meetings, search the org directory, fetch meeting transcripts | `backend/src/services/graph/**`, `services/directory.rs`, `services/meeting_scheduling.rs`, `services/meeting_transcript.rs` | optional; only active if `GRAPH_*` env vars are set. Every **write** goes through the "G1" governed-write stack (`services/graph/writes.rs`) |
| OpenAI | extract structured fields from an uploaded intake document; summarise a meeting transcript | `backend/src/services/ai_extraction/**` | optional; only if `OPENAI_API_KEY` set. **Every call passes a PHI/PII pre-egress gate first** (`ai_extraction/phi_gate.rs`) — if the text looks like it contains protected health information, nothing is sent |

Neither Microsoft Graph nor OpenAI is modelled as an `.appfw` data source — they
are not CRUD stores, so they are plain hand-written service clients.

## 2.8 The four feature specs

The design intent is captured in [`.appfw/specs/`](../../.appfw/specs/). Read
[`.appfw/specs/000-INDEX.md`](../../.appfw/specs/000-INDEX.md) first — it
reconciles the four where they overlap.

| Spec | Owns | Implemented as |
|------|------|----------------|
| 001 auth / RBAC / tenancy | actor claims, single-tenant posture, one `.rego` per table, the Rego row-filter layer | `.appfw/model/**` + policies |
| 002 gate / workflow engine | the state machine, eligibility, transitions, `AuditEvent`, the service-layer authorization split | `backend/src/services/{approval_state_machine,gate_eligibility,transition,gate_review,workspace,audit,notification}.rs` |
| 003 MS Graph provider | the governed Graph client, `Meeting` + `GraphSubscription` entities, `Meeting.process_transcript` | `backend/src/services/graph/**`, `services/meeting_*.rs` |
| 004 AI / storage | the OpenAI egress boundary + PHI gate, document storage, notifications writer | `backend/src/services/ai_extraction/**` (egress boundary partially built; RAG/knowledge-base deferred) |

All four are status **`accepted-pending-decisions`** — implemented, but a handful
of product decisions ([`docs/architecture/open-decisions.md`](../architecture/open-decisions.md))
could still change generated output or behaviour. The biggest is **P5**: the
authoritative Excel gate matrix is not in the repo, so the gate DAG is
provisional.
